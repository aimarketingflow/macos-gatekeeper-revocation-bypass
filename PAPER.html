Abstract

This paper documents a vulnerability in macOS Tahoe's certificate revocation enforcement architecture that allows an attacker on the same network to bypass Gatekeeper's "Malware Blocked" protection for applications signed with revoked Developer ID certificates. The vulnerability was discovered through firewall-based constraint analysis — a methodology that uses local firewall blocking to simulate network-layer attacks on macOS security daemons. We demonstrate three attack vectors of decreasing complexity: Thunderbolt + NTP MITM (~105 minutes), Thunderbolt + DNS poisoning (~5 minutes), and WiFi-only DNS poisoning (~5 minutes), all producing the same result — syspolicyd's rule 11 fail-open policy engages when OCSP is unreachable, allowing revoked-certificate applications to launch with only a bypassable "unidentified developer" prompt instead of the non-bypassable "Malware Blocked" dialog. The root cause is a triple failure: CRLite — Apple's offline bloom filter-based revocation system — is present in the valid.sqlite3 schema but disabled via feature flags (UseCRLite is disabled); valid.sqlite3 contains zero Developer ID certificate serials; and the fallback policy (rule 11) explicitly allows execution when revocation status cannot be determined. CRLite is the obvious solution to the fail-open problem — it provides offline revocation checking that does not depend on DNS-defeatable OCSP — yet Apple built it, shipped the schema, and then disabled it. Apple deployed a cert-specific OCSP responder fix on July 22, 2026 — eight days after receiving the researcher's rebuttal — but the architectural fail-open policy remains unchanged. Any revoked Developer ID certificate not yet covered by the responder update remains exploitable. The disclosure timeline documents 13 Apple Security Bounty tickets filed over seven weeks, all closed without acknowledgment as vulnerabilities. Apple's central objection — that the user "affirmatively overrides a Gatekeeper warning" — is contradicted by evidence that the attack removes the non-bypassable dialog entirely, replacing it with a standard bypassable prompt that contains no revocation information. Publication rights analysis confirms that Apple's bounty T&C create a reward incentive for non-disclosure, not a legal prohibition, and that publication after vendor denial is supported by industry-standard coordinated disclosure frameworks and multiple documented precedents.

§1. Discovery — Firewall-Blocking Methodology

1.1 Research Approach

The vulnerability described in this paper was discovered through a methodology we term firewall-based constraint analysis: using third-party network firewalls to voluntarily block system daemons' network access, then observing how macOS security subsystems behave when their telemetry channels are severed. The logic is straightforward — if blocking a daemon's network traffic via a local firewall reveals a security degradation, then an attacker performing the same traffic blocking at the network layer (via ARP MITM, DNS poisoning, or NTP interception) achieves the same result without requiring any software installation on the victim machine.

This methodology was applied using LuLu, a free and open-source macOS firewall by Objective-See, which allows per-process network traffic control. By systematically blocking outbound traffic from timed (the macOS time synchronization daemon), trustd (the certificate validation daemon), and other security-critical processes, we observed behaviors that would normally be masked by the daemons' ability to self-heal through network communication.

1.2 Initial Observation: timed WrongPredictState

On May 31, 2026, a sysdiagnose capture from Mac A (macOS Tahoe, Apple Silicon) revealed 1,583 lines of timed log output showing repeated STF,WrongPredictState entries during a period when LuLu was blocking timed's outbound NTP traffic.

Observed: STF,WrongPredictState,Current,rtc,22244087.289,utc,801816309.914... (timed.txt, line 1151) — five occurrences at lines 1151, 1160, 1277, 1409, and 1530.

Observed: May 30 log entries showing "We are already waiting on the network" — indicating timed was starved of NTP access and could not self-correct.

Source: Research evidence E17 — sanitized timed.txt from sysdiagnose_2026_05_31_16_37_14

Interpretation and Limits: The WrongPredictState entries indicate timed entered an error state when denied NTP access. The critical observation is that this state did not self-heal after the firewall block was removed — the daemon remained in a degraded state for approximately eight days. This persistence is the foundational observation for the entire attack chain: network-layer traffic manipulation produces lasting security degradation that survives reboots and network restoration.

1.3 LuLu Timeline and Causal Link

Observed: A timeline reconstruction (Research evidence E16) documents LuLu's on/off windows across approximately eight days. LuLu was disabled during active attack testing and enabled during idle periods. The ~8 days of blocked recovery for timed and trustd establishes that the firewall block, not the attack itself, was the primary cause of the persistent degraded state.

Source: Research evidence E16 — "Total idle time where recovery was blocked: ~8 days"

Observed: The forensic analyzer script (Research evidence E15) includes LuLu block/deny/drop event counting and LuLu-vs-error correlation per process, providing the methodological basis for identifying the causal link between firewall blocking and daemon degradation.

1.4 From Firewall to Network Attack

The discovery methodology's key insight: if a local firewall blocking timed's NTP traffic causes persistent WrongPredictState, then an attacker who intercepts or blocks NTP traffic at the network layer achieves the same result. The attacker does not need to install software, modify system files, or have any access to the victim machine — only network position.

This insight motivated the subsequent attack-chain development: ARP MITM for network positioning, NTP interception for clock manipulation, and DNS poisoning for OCSP/notarization blindness. Each layer replicates a firewall block at the network level.

§2. NTP Attack Vector — ARP MITM and Clock Manipulation

2.1 Attack Architecture

The first demonstrated attack vector uses ARP spoofing to position the attacker as the default gateway for the victim machine, then intercepts NTP responses to manipulate the victim's system clock. This was demonstrated across two campaigns using Thunderbolt bridge and WiFi vectors.

Observed: On June 4, 2026, an ARP MITM attack against Mac B produced a settimeofday() call with adjust,90.001640081,success,1 — proving that timed accepted a spoofed NTP offset of +90 seconds per poll.

Source: Research evidence E01 — victim_timed_log.txt, line 728

Observed: Pre-attack baseline (Research evidence E13) confirmed the clock was stable before the attack, establishing the before/after comparison.

2.2 Clock Drift Accumulation

The attack accumulates clock drift at approximately +90 seconds per NTP poll. With default timed polling intervals, a +10 minute clock shift is achievable in approximately 105 minutes of sustained attack.

Observed: June 10 research milestone — Thunderbolt Bridge attack achieved +179s drift with 553 NTP packets intercepted, and OCSP failure was confirmed during this window.

Observed: June 12 research milestone — WiFi ARP MITM achieved +89.85s clock shift, with persistence through reboot.

Observed: June 16 research milestone — NTP starvation confirmed over 3 hours 9 minutes, with 0 of 33 NTP packets reaching the victim, producing +25s persistent offset.

2.3 Security Impact of Clock Manipulation

Observed: A +10 minute clock shift causes trustd OCSP revocation checking to fail with error -1009, and syspolicyd (Gatekeeper) falls back to allow with "rule 11 applies - allow=1".

Source: Research evidence E03, E04 — Gatekeeper degradation report and raw syspolicyd log

Interpretation and Limits: The clock shift itself is not the final vulnerability — it is the mechanism that triggers the security degradation. The actual bypass occurs when syspolicyd's fail-open policy engages upon OCSP failure. The clock shift is one of three demonstrated vectors for achieving this condition; DNS poisoning (§3) achieves the same result faster and without requiring clock manipulation.

§3. DNS Poisoning Vector — OCSP and Notarization Blindness

3.1 Attack Architecture

The second attack vector bypasses the need for clock manipulation entirely. Instead of intercepting NTP traffic, the attacker poisons DNS responses for Apple's security-critical domains, causing the victim's trustd to believe OCSP servers are unreachable. This achieves "full security blindness" — the victim machine cannot perform certificate revocation checks, notarization ticket verification, or XProtect updates.

3.2 Three-Channel Blindness

Observed: On July 7, 2026, Campaign 2.0 achieved "Full 3-Channel Blindness" in approximately 6 minutes. The three channels are: (1) OCSP revocation checking, (2) notarization ticket verification, and (3) XProtect malware signature updates.

Source: Research evidence E07 — Campaign 2.0 test log, line 48: "Full 3-Channel Blindness Achieved in ~6 Minutes"

Observed: The attack poisoned 46 Apple security domains, redirecting them to a sinkhole address. macOS attempted CDN bypass paths when primary domains were poisoned, requiring additional domains to be included in the poison set.

Source: Research evidence E08 — Campaign 2.0 findings report

Interpretation and Limits: The 6-minute timeframe represents the time from attack initiation to confirmed blindness. The actual OCSP cache expiration may vary by machine and prior state. The 46-domain count is not reproduced here per sanitization plan — domains are referenced generically as "Apple OCSP and notarization domains."

§4. Gatekeeper Bypass Proof — syspolicyd Fail-Open

4.1 The Critical Transition

The core vulnerability is syspolicyd's fail-open policy when OCSP is unreachable. When trustd cannot obtain revocation status for a certificate, syspolicyd applies rule 11, which explicitly allows execution.

Observed: 366 lines of syspolicyd log from July 7, 2026 (Campaign 1.5) show the transition from rule 3 (normal enforcement) to rule 11 (fail-open) at 18:04:59, coinciding with OCSP check failures.

Source: Research evidence E06 — BYPASS_PROOF.txt, line 29: syspolicyd[476:2c93a] [com.apple.securityd:gk] rule 11 applies - allow=1

4.2 Revoked Certificate App Launch

The bypass was verified using a macOS application signed with a revoked Developer ID certificate. The sample — ChatGPT Desktop for macOS v1.2026.049, signed by OpenAI, L.L.C. (Developer ID team 2DC432GLL2) — had its certificate revoked on May 8, 2026, following a publicly reported supply chain incident.

Source: Verification analysis §2.1 — sample properties table

This sample is ideal for verification because its revocation is exclusively detectable via online OCSP — it is not in the local gkopaque.db whitelist, not detectable via notarization ticket cache, and not flagged by XProtect. The only variable between the app being blocked and being allowed is DNS reachability.

4.3 Positive Control: Bypass Confirmed (July 9, 2026)

Phase 1 — Pre-attack baseline (OCSP reachable):

Observed: spctl -a -vv returned CSSMERR_TP_CERT_REVOKED — revocation correctly detected, app cannot be opened.

Phase 2 — During attack (DNS poisoning active):

Observed: spctl -a -vv returned REJECTED: source=Unnotarized Developer ID — the rejection reason changed from a hard block (non-bypassable "Malware Blocked" dialog) to a soft block (bypassable "unidentified developer" prompt).

Source: Verification analysis §2.3 — "The DNS poison prevented macOS from discovering the revocation, downgrading the security response."

Phase 3 — During attack (Finder launch):

Observed: User right-clicked the app → Open. Application launched successfully. ChatGPT UI rendered, connected to OpenAI servers, and registered as a Login Item for background persistence across reboots.

Source: Verification analysis §2.3 — "A macOS application signed with a revoked Developer ID certificate was successfully launched via Finder during active DNS poisoning."

Observed: syspolicyd log shows evaluateScanResult: 2 with flags 0, 0, 1, 0, 0, 0, 0 — no malware detected (0), no revocation detected (0), allowed to proceed (1), no notarization ticket found (0).

Source: Verification analysis §2.3 — FULL_BYPASS_REPORT.md, lines 221-223

4.4 The Security Boundary Crossed

Interpretation and Limits: The attack changes the Gatekeeper dialog from "Malware Blocked and Moved to Trash" (non-bypassable — no Open button exists) to "Unidentified developer" (bypassable — right-click → Open). This is not the user "overriding a warning" — the attack removes the security-relevant information entirely. The user never sees revocation information. The same dialog appears for any non-App-Store app, giving the user no indication that the certificate has been revoked.

§5. CRLite Disabled — The Missing Offline Defense

5.1 CRLite Feature Flag Disabled

Direct trustd log capture on macOS Tahoe confirms CRLite is explicitly disabled via feature flags:

trustd: UseCRLite is disabled (via feature flags)
trustd: skipping further reads. no CA Revocation Additions found: (null)

In Apple's open-source Security-61901.120.67 release, the enforcement function _SecTrustUseCRLiteEnforcement() returns false. CRLite tables exist in the valid.sqlite3 schema but are never consulted because the feature flag is off. The infrastructure was built, shipped, and then turned off.

Source: Campaign 5.0 trustd log capture, July 24, 2026; Apple open-source Security-61901.120.67

5.2 CRLite Tables Present But Empty

Direct database queries against valid.sqlite3 on two Tahoe machines confirm the CRLite tables exist but contain zero rows:

TableMac A (Tahoe/M1)Mac B (Tahoe/M3)
crlitefilters0 rows0 rows
crlitefiltercoverage0 rows0 rows

Even if the feature flag were enabled, there is no data for CRLite to consult. Apple built the schema, added the tables to db_format=8, and never populated them.

Source: Direct sqlite3 queries against valid_maca.sqlite3 and valid_macb.sqlite3, July 24, 2026

5.3 No Developer ID Serials in valid.sqlite3

The valid.sqlite3 serials table contains ~72,000 revoked serials, but none of them are Apple Developer ID certificates. A direct query for the test certificate's serial returns zero matches:

SELECT COUNT(*) FROM serials WHERE serial = X'68A68AF8A434EE4FDE46F8680B23BDCC';
→ 0

valid.sqlite3 covers web PKI certificate authorities only — not Apple's own Developer ID code signing infrastructure. This means the local serial database provides zero coverage for the exact class of certificates Gatekeeper is responsible for validating.

Source: Direct sqlite3 query, confirmed on both Tahoe machines, July 24, 2026

5.4 The Triple Failure

When OCSP is unreachable (via DNS poisoning), three independent layers of revocation defense all fail simultaneously on macOS Tahoe:

LayerStatusCoverage
CRLite (offline bloom filter)DISABLED via feature flagsZero — never consulted
valid.sqlite3 (local serials)Present but no Developer ID serialsZero — wrong scope
syspolicyd rule 11 (fallback policy)Fails open: allow=1Actively harmful — allows execution

OCSP was the sole remaining defense — and it is defeatable by a 3-second DNS poisoning window. With CRLite disabled, there is no offline fallback. The entire revocation enforcement for Developer ID certificates depends on a single, network-reachable OCSP request.

5.5 CRLite Is the Obvious Solution

CRLite is the obvious solution to the fail-open problem. It provides offline revocation checking using bloom filters — no network access required. An attacker poisoning DNS cannot defeat a local bloom filter lookup. Mozilla deployed CRLite in Firefox in 2021; Apple built the same architecture into trustd but never enabled it.

Apple's 2020 commitment to "strong protections against server failure" (§15) was supposed to be fulfilled by CRLite. Ars Technica noted in their 2020 coverage: "A revocation method known as CRLite may ultimately provide a solution to this failing." Six years later, CRLite exists in Apple's trustd source code but is disabled via feature flag. The solution identified in 2020 was implemented but never activated.

5.6 Apple's July 28 Admission Confirms the Gap

Apple's July 28, 2026 response confirms the fail-open is intentional and that their sole mitigation is a cached OCSP response — not an offline database:

"When a revocation check cannot reach the responder and the machine holds no previously cached revoked response for that certificate, the evaluation soft-fails."

"A cached revoked response is pinned permanently."

This means Apple's entire revocation defense for Developer ID certificates depends on: (1) the victim having previously contacted the real OCSP server for that specific certificate, and (2) the cached response surviving on disk. For any previously-unseen revoked certificate, a fresh Mac, or a machine where the attacker controls DNS from first contact, there is zero protection. CRLite would close this gap entirely — but it is disabled.

Source: Apple Security Bounty ticket OE1107167498810, response dated 7/28/26

§6. Negative Controls

6.1 Unnotarized App Rejection (July 7, 2026)

Observed: An unnotarized test app signed with the researcher's own Developer ID (but not notarized) was REJECTED on both Tahoe machines. spctl -a -vv returned "rejected, source=Unnotarized Developer ID" on both Mac A and Mac B.

Source: Research evidence E11 — UnnotarizedTest.app

Interpretation and Limits: This narrows the bypass scope to revoked-but-previously-notarized certificates. Rule 13 (deny unnotarized) still functions during the attack. The bypass only affects the OCSP revocation check path — meaning a notarized app signed with a stolen or revoked Developer ID certificate would pass because trustd cannot check revocation status.

6.2 Post-Fix Control (July 14, 2026, macOS 26.5.2)

Observed: After updating to macOS 26.5.2, the same ChatGPT DMG with OCSP reachable produces "Malware Blocked and Moved to Trash" — no override possible.

Source: Verification analysis §2.5 — "Control test (July 14, macOS 26.5.2): Same DMG, OCSP reachable: 'Malware Blocked and Moved to Trash' — no override possible."

Interpretation and Limits: This control confirms that the bypass is specific to the pre-fix Tahoe versions. However, the fix version's behavior when OCSP is poisoned has not been independently tested by the researcher. §7. Attack Simplification — WiFi-Only Bypass

7.1 Three Demonstrated Vectors

The attack chain was progressively simplified from requiring physical access (Thunderbolt) to requiring only WiFi proximity:

Source: Research evidence attack-chain map — three demonstrated vectors

7.2 WiFi-Only Bypass (July 15, 2026)

Observed: On July 15, 2026, a WiFi-only attack was demonstrated. No Thunderbolt cable, no NTP manipulation, no physical access to the victim machine. The attacker and victim were on the same WiFi network. Time to exploit: under 5 minutes from attack start to successful bypass.

Source: Research evidence E10 — "Time to exploit: under 5 minutes from attack start to successful bypass" (line 7)

Observed: 44 OCSP queries were blocked during the attack. The attack used DNS poisoning only — no clock manipulation was required.

7.3 Real-World Attack Scenario

Interpretation and Limits: The WiFi-only vector means any attacker on the same network (coffee shop, hotel, airport, corporate WiFi) can execute the attack. The victim requires no software installation, no click-through, and no interaction — the attack is entirely network-level. The persistence of the bypass after attack cessation (observed in earlier campaigns) means the attacker can leave the network before the victim attempts to open any application.

The attack is particularly effective against sleeping Macs: a laptop with its lid closed but WiFi active (extremely common behavior) can be attacked overnight, allowing all OCSP caches to expire. When the user wakes the machine and opens an app, Gatekeeper's fail-open policy is already engaged.

§9. Publication Rights and Legal Context

9.1 Apple Security Bounty Terms

Apple's published Terms and Conditions contain a single disclosure restriction, tied exclusively to award eligibility:

"For a reported security vulnerability affecting any Apple platform to be eligible for an Apple Security Bounty award, you must not disclose it to anyone other than Apple until after Apple has released a software update and published a security advisory for the reported security vulnerability."

Source: Publication rights researchQ1 — Apple Security Bounty T&C, accessed 2026-07-23

The consequence of early disclosure is loss of bounty eligibility, not a legal injunction, NDA breach, or IP claim. There is no stated embargo period — the restriction is open-ended until Apple ships a fix AND publishes an advisory.

9.2 Rights After Denial

If Apple closes a report without fixing it or denies the bounty, the T&C condition ("until after Apple has released a software update and published a security advisory") can never be satisfied through Apple's action. This creates an indefinite de facto embargo — but only for award eligibility, not as a legal prohibition.

The researcher's options after denial:

  1. Publish immediately — forfeit any future eligibility (already denied, so no practical loss)
  2. Wait for Apple to fix — retain theoretical eligibility (but Apple has already denied)
  3. Follow industry-standard 90-day CVD — disclose after 90 days from report regardless of fix status

No NDA, IP assignment, or injunctive clause prevents publication. The researcher's work product remains their own. The published T&C contain no IP assignment, license grant, copyright transfer, or work-for-hire clause.

12.4 The "Offline Tradeoff" Rebuttal

Apple argued: "Failing closed would block apps from launching whenever a device is offline."

This argument has three weaknesses:

  1. CRLite would solve this — Apple already built CRLite, an offline bloom filter-based revocation system that requires no network access. It is present in the valid.sqlite3 schema but disabled via feature flags. If CRLite were enabled, the "offline vs. security" tradeoff would disappear — the system could fail closed for revoked certificates without requiring network access. Apple built the solution to their own argument and then turned it off.
  2. The attack is not "offline" — the victim's internet works perfectly. Only Apple security domains are poisoned. The user can browse the web, check email, and use all services normally. Apple's offline scenario is not the threat model.
  3. The tradeoff is configurable — other vendors implement graduated responses: block execution if revocation status is "unknown" for high-risk operations (first launch, Developer ID), allow for low-risk (previously-validated apps). Apple chose the most permissive option for all cases.

§14. CVE Filing Strategy and MITRE CNA-LR Path

14.1 Two-Stage Approach

CVE assignment for Apple products follows a two-stage process:

  1. Stage 1: Apple as CNA (expected outcome: decline) — Apple is the CVE Numbering Authority for macOS. Having called the behavior "intended," they are unlikely to self-assign a CVE. This is the expected first step, not the goal.
  2. Stage 2: MITRE CNA-LR dispute (target: 60-75% success) — Once Apple declines, the researcher requests MITRE's CNA of Last Resort to assign under the dispute resolution process. Per CNA Rules v4.0: "If the CNA does not assign, for any reason, then another CNA with appropriate scope can assign."

14.2 The GHSA Contradiction Rebuttal

Before filing the CVE, the researcher will post a rebuttal to Apple's ticket asking them to explain the inconsistency between their fix for GHSA-8f6j-263m-g72x and their "intended behavior" classification of the same vulnerability class in trustd. The three questions:

  1. What is the policy basis for treating OCSP revocation bypass as fixable in the App Store Server Library but "intended" in macOS trustd?
  2. Is the distinction based on failure mode (stale acceptance vs. fail-open), product class (server library vs. OS), or something else?
  3. If the offline-launch tradeoff is the reason, why does that tradeoff not apply to server-side code (which also experiences network failures)?

Apple's response (or silence) becomes evidence for the CNA-LR dispute. If they cannot articulate a meaningful distinction, their "intended" claim is exposed as inconsistent.

14.3 CVE Program Rules That Support Assignment

Five provisions of the CVE Program's operational rules support assignment despite Apple's "intended" claim:

  1. Rule 4.1.4 — Insecure Default Configuration Settings: "Insecure default configuration settings SHOULD be determined to be Vulnerabilities." (CNA Rules v4.1.0) — The fail-open is an insecure default. CRLite — the offline defense that would prevent fail-open — is disabled by default.
  2. "Documented Behavior" exception does NOT apply — The fail-open is not documented in Apple's Platform Security Guide, was discovered through research, and Apple's own 2020 promise to deliver "strong protections against server failure" acknowledges the behavior as a problem worth fixing.
  3. CNA-LR process: "The CNA with the most appropriate scope gets the first opportunity to assign. If the CNA does not assign, for any reason, then another CNA with appropriate scope can assign." (CNA Rules v4.0)
  4. "CVE is not about fixes": MITRE explicitly stated this in the CVE-2024-37408 dispute. Apple's intent to not fix does not prevent assignment.
  5. Publicly disclosed: "CNAs SHOULD assign a CVE ID if: the CNA has reasonable evidence to determine the existence of a Vulnerability, and the Vulnerability has been or is expected to be Publicly Disclosed." — Apple's open-source trustd code constitutes public disclosure.

§15. Apple's 2020 Promise — "Strong Protections Against Server Failure"

15.1 The Big Sur OCSP Outage (November 2020)

On November 12, 2020, macOS Big Sur's release overwhelmed Apple's OCSP responder infrastructure, causing widespread app launch failures across the Mac ecosystem. The incident began when a server-side misconfiguration interfered with macOS's ability to cache Developer ID OCSP responses, combined with an unrelated CDN misconfiguration. Users experienced multi-minute hangs when launching third-party applications.

The incident drew significant public attention, most notably from security researcher Jeffrey Paul, whose blog post "Your Computer Isn't Yours" raised privacy concerns about unencrypted OCSP queries to ocsp.apple.com. Jeff Johnson identified the root cause: trustd connecting to ocsp.apple.com with OCSP configured as a soft failure.

15.2 Apple's Official Response and Three Commitments

On November 15, 2020, Apple updated their support document "Safely open apps on your Mac" with a new "Privacy protections" section. The statement included three explicit commitments for the coming year:

"In addition, over the next year we will introduce several changes to our security checks:"

  • "A new encrypted protocol for Developer ID certificate revocation checks"
  • "Strong protections against server failure"
  • "A new preference for users to opt out of these security protections"

Apple separately told iPhone in Canada that the outage was caused by "a server-side misconfiguration that specifically interfered with macOS being able to cache Developer ID OCSP responses," and that they had fixed it through a server-side update allowing longer OCSP cache durations.

Apple fulfilled two of three promises. The middle commitment — "strong protections against server failure" — was only partially addressed. Apple fixed accidental server failure (the 2020 outage was a misconfiguration/capacity issue) by improving OCSP caching durations. But adversarial server failure — an attacker blocking ocsp.apple.com for 3 seconds via DNS poisoning — produces the identical outcome: revocation check fails, app launches. Apple treats the accidental case as a bug worth fixing and the adversarial case as "intended behavior."

15.4 The Six-Year Gap

The fail-open behavior that caused the 2020 Big Sur outage is the same behavior demonstrated in this paper's 2026 attacks. The difference is causation:

  • 2020: Server-side misconfiguration → OCSP unreachable → fail-open → apps won't launch (but revocation bypassed)
  • 2026: Attacker DNS poisoning → OCSP unreachable → fail-open → revoked app launches (revocation bypassed)

Same mechanism. Same fail-open. Same security impact (revocation checking skipped). Apple acknowledged the first as a problem worth fixing. They call the second "intended behavior."

Ars Technica noted in their 2020 coverage: "A revocation method known as CRLite may ultimately provide a solution to this failing." Six years later, CRLite exists in Apple's trustd source code but is disabled via feature flag (_SecTrustUseCRLiteEnforcement() returns false). The solution identified in 2020 was implemented but never activated.

15.5 Implications for Disclosure

Apple's 2020 statement has two implications for the current disclosure:

  1. It contradicts "intended behavior." Apple explicitly promised "strong protections against server failure" — the exact condition our attack exploits. If the fail-open was truly intended, why promise to protect against it? The promise acknowledges the behavior as a problem; the 2026 denial reframes it as acceptable.
  2. It establishes a six-year unfixed timeline. The vulnerability was publicly identified in 2020, Apple committed to fixing it, and six years later the core security issue remains unaddressed. This timeline is relevant for CVE assignment (demonstrating the issue is not newly discovered but is a long-standing unfixed problem) and for public disclosure (the finding is not a zero-day but a confirmation that a known issue remains exploitable).
