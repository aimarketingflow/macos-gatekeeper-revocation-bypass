Apple Product Security Jul 28, 2026, 7:52 PM
Thanks for the detailed follow-ups, and for correcting your own analysis on July 24. That was useful and it is appreciated. We have reviewed this with the team that owns trust evaluation. The behavior you observed is intended. When a revocation check cannot reach the responder and the machine holds no previously cached revoked response for that certificate, the evaluation soft-fails. Failing closed in that situation would block apps from launching whenever a device is offline, behind enterprise egress filtering, on a captive portal, or on an unreliable network, which is not a tradeoff we can make. The protection that governs this case is that a cached revoked response is pinned permanently. Once a machine has seen the revocation, it stays blocked, and that is not affected by later network conditions. Your own July 24 testing shows exactly that, on both machines. On the log lines cited as proof, trustd is published as open source, so you can verify this directly rather than take our word for it: https://github.com/apple-oss-distributions/Security/tree/Security-61901.120.67 In particular, "ocsp responder: ... did not include status of requested cert" is emitted from SecORVCConsumeOCSPResponse in trust/trustd/SecRevocationServer.c, which is reached only after a response has been received and parsed successfully, so it does not indicate a blocked query. The "nextUpdate N days ago" message comes from SecOCSPSingleResponseCalculateValidity in SecOCSPResponse.c and refers to a cached response, not a network attempt. The pinning behavior is in SecOCSPCache.c. Note that this is a published snapshot, so line numbers will differ from current sources, though the functions are stable.

THE FAIL-OPEN PATH File: trust/trustd/SecRevocationServer.c The revocation check flow in SecPathBuilderCheckRevocation proceeds through these layers: 1. CRLite → 2. Valid info DB → 3. Stapled OCSP → 4. OCSP cache → 5. Network fetch → 6. If timeout: SecRVCSetFinishedWithoutNetwork() SecRVCSetFinishedWithoutNetwork does the following: static void SecRVCSetFinishedWithoutNetwork(SecRVCRef rvc) { rvc->done = true; SecRVCUpdatePVC(rvc); (void)SecPathBuilderDecrementAsyncJobCount(rvc->builder); } It sets done=true with no error, no revocation determination, and no isRevoked flag. The evaluation completes as if revocation was never checked. The timeout that triggers this path: #define OCSP_RESPONSE_TIMEOUT (3 * NSEC_PER_SEC) Three seconds of OCSP unreachability → evaluation completes with no revocation result → syspolicyd allows execution. 2. CRLite: BUILT BUT DISABLED Same file, in SecPathBuilderCheckRevocation: if (TrustdVariantAllowsFileWrite() && _SecTrustUseCRLite() && SecRVCCheckCRLite(rvc)) { if (_SecTrustUseCRLiteEnforcement()) { SecRVCSetFinishedWithoutNetwork(rvc); continue; } } And in SecRVCProcessCRLiteResults: } else { secnotice("validupdate", "CRLite result not being enforced (revoked=%d), falling back to Valid", revoked); } A complete offline revocation system exists — SecRVCCheckCRLite, SecRVCProcessCRLiteResults, SecRVCSetCRLiteDeterminedErrorResult — that would resolve the fail-open without requiring network access. It is disabled via _SecTrustUseCRLiteEnforcement(). Our testing confirms it returns false on Tahoe. If cache pinning alone is sufficient protection, why was this fallback built? The log message "CRLite result not being enforced (revoked=%d), falling back to Valid" explicitly acknowledges that disabling CRLite enforcement means falling back to the Valid database — which contains zero Developer ID serials. 3. THE CACHE IS ACKNOWLEDGED AS UNTRUSTED ON macOS File: trust/trustd/SecRevocationServer.c, SecORVCConsumeOCSPResponse: #if TARGET_OS_IPHONE /* Performance optimization since we don't write invalid responses to the cache. */ if (!fromCache) { __Require_Quiet(SecOCSPResponseVerify(ocspResponse, rvc, ...), errOut); } #else /* Always check the OCSP response signature and verify the response (since the cache is user-modifiable). */ __Require_Quiet(SecOCSPResponseVerify(ocspResponse, rvc, ...), errOut); #endif The macOS path always re-verifies because the cache is "user-modifiable."
